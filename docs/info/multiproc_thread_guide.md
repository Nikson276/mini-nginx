# Multiprocessing, Threads, Asyncio

## Multiprocess proxy (without multiprocessing)

- **Зачем**: один процесс asyncio упирается в одно CPU‑ядро; для целей 1000+ RPS разумно масштабироваться по процессам.
- **Как**: благодаря `reuse_port=True` на основном сокете и сокете метрик можно запустить несколько процессов `python -m proxy.main` с одинаковым `listen`.
- **Пример**:

```bash
CONFIG_PATH=./config.yaml PYROSCOPE_APPLICATION_NAME=proxy-multi python -m proxy.main &
CONFIG_PATH=./config.yaml PYROSCOPE_APPLICATION_NAME=proxy-multi python -m proxy.main &
wait
```
- ядро распределяет входящие подключения по процессам, достигая суммарного RPS примерно `N × RPS_одного_процесса` (в пределах ресурсов машины).


### 1. Когда вообще нужен `multiprocessing`, если можно «просто запустить 4 процесса»?

- **«Просто 4 процесса через shell/systemd/Docker»**  
  - **Когда уместно**: сервисный софт (веб‑серверы, прокси, очередники), где нормальная практика – менеджер процессов снаружи: systemd, supervisord, Docker/Compose, Kubernetes.  
  - **Плюсы**: проще, нагляднее, лучше интегрируется с мониторингом/рестартом, не тянет в код всю логику оркестрации воркеров.

- **Библиотека `multiprocessing` внутри приложения** обычно нужна, когда:
  - **Нужен программный контроль над воркерами из одного процесса**:
    - динамически поднимать/гасить воркеры в ответ на нагрузку;
    - запускать короткоживущие job’ы в `Pool`/`ProcessPoolExecutor`;
    - делать «map over data» в стиле `pool.map(...)`.
  - **CPU‑bound задачи**:
    - обход GIL: тяжёлые вычисления в нескольких процессах (парсинг, ML, крипта, анализ логов и т.п.).
  - **Нужен явный обмен данными/очередями между процессами**:
    - `multiprocessing.Queue`, `Pipe`, `Manager`‑объекты и т.д., когда именно твой процесс — «мастер», а воркеры завязаны на его жизненный цикл.
  - **Ты пишешь не сервис, а библиотеку/утилиту**, которая сама должна управлять параллелизмом, а не надеяться на внешнего оркестратора.

**В контексте прокси**:  
для повышения RPS обычно **достаточно внешнего мультипроцессного запуска** (systemd, Docker, просто несколько `python -m proxy.main`). `multiprocessing` внутри добавит сложности (fork/spawn, IPC, graceful shutdown, SIGHUP/конфиги), а реального выигрыша по RPS по сравнению с «4 отдельных процесса» не даст.

### 2. AsyncIO vs threading для IO‑bound в прокси: плюсы/минусы и влияние на RPS

У тебя сейчас:

- один **asyncio event loop**;
- **асинхронные сокеты** (и к клиентам, и к upstream’ам);
- почти всё IO уже неблокирующее.

Сравним:

#### **AsyncIO (как у тебя сейчас)**

- **Плюсы:**
  - **Один поток, один event loop** → нет гонок данных внутри Python‑кода, почти не нужны блокировки;
  - **Дешёвые coroutines** → можно держать тысячи одновременных соединений;
  - Хорошо подходит для **массового сетевого IO** (прокси, чат‑серверы, HTTP‑сервисы).
- **Минусы:**
  - Всё крутится **на одном ядре** → потолок RPS ограничен одним CPU‑ядром;
  - Любой «тяжёлый» код (логирование, сложные вычисления) **блокирует весь loop**;
  - Нужно строго следить, чтобы не просочились блокирующие вызовы (sync‑библиотеки, медленный диск и т.п.).

#### **Threading для IO‑bound**

- **Плюсы:**
  - Хорошо работает с **старым/блокирующим кодом** (обычный `requests`, блокирующий драйвер БД и т.д.);
  - Можно использовать **несколько ядер**, если в потоке есть блокирующее IO + чуть CPU, но:
    - GIL всё равно ограничивает чистый CPU, но многие IO‑heavy задачи выигрывают от того, что ядра параллельно ждут/обрабатывают.
- **Минусы:**
  - **OS‑нитей много не поднимешь**: тысячи потоков → тяжёлый контекст‑свитчинг, рост памяти;
  - Нужны **блокировки, очереди, синхронизация**, что усложняет код и даёт contention;
  - В Python классический «thread‑per‑connection сервер» обычно хуже масштабируется по числу коннектов, чем event‑loop + coroutines.

#### Как это влияет на RPS именно для твоего прокси

- Сейчас твой путь:
  - один процесс asyncio **уже умеет держать тысячи коннектов**;
  - упор идёт в **CPU одного ядра + логирование + локи в метриках/пуле**.
- Добавление **threading поверх уже асинхронного кода**:
  - почти не поможет RPS, пока основной код и так неблокирующий;
  - добавит сложность (многопоточность + async) и новые точки блокировок.
- Реалистичная стратегия масштабирования RPS для такого прокси:

1. **Оптимизировать один процесс asyncio**:
   - минимизировать работу в hot‑path (логи, локи, лишние await’ы);
   - убедиться, что нет случайных блокирующих вызовов.

2. **Масштабировать по процессам**, а не по потокам:
   - несколько независимых процессов прокси с `reuse_port=True`;
   - каждый процесс — свой event loop на своём ядре;
   - ядро/OS раскидывает коннекты между процессами.
   - Это даёт почти линейный рост суммарного RPS при достаточном CPU.

3. **Потоки использовать точечно**, если нужно:
   - вынести редкие/тяжёлые блокирующие операции в `ThreadPoolExecutor` (`loop.run_in_executor`) — не для сетевого IO (оно уже async), а для, например, тяжёлого CPU или старых sync‑клиентов.

### Краткий ответ по выбору

- **Для повышения RPS твоего прокси:**
  - **оставаться на asyncio** для обработки коннектов;
  - **масштабироваться процессами**, а не потоками;
  - **threading** использовать только как адаптер для единичных блокирующих операций, а не как основную модель сервера.

- **`multiprocessing` как библиотека** имеет смысл:
  - для CPU‑тяжёлых задач и batch‑обработки;
  - или когда сам процесс должен программно рулить пулом воркеров.  
  Для сетевого прокси проще и надёжнее управлять несколькими процессами извне (systemd/Docker) + `reuse_port`, как ты уже сделал.
